# ADR 0001：显式责任模块与统一构建

状态：接受于 2026-10-03；2026-10-04 补充论证，不改变决定。读者：架构维护者。

本记录保存当时完整决定；目录、旧入口、Schema中转和重定向策略已由 [ADR 0004](0004-physical-modules-and-public-api.md) 替代。当前实现以新决定和模块API为准。

## 背景

项目同时包含博客应用、书籍构建、终端分页、移动发布和运行观测。它们变化原因不同，早期目录没有清楚表达责任：博客适配位于通用构建内部，服务器脚本缺少契约资料。

需要隔离依赖与理解成本，同时保留 Astro 固定目录、公开浏览器地址和服务器命令。当前没有六套独立发布周期或真正独立消费者。

## 备选方案

| 方案                 | 收益                               | 代价/不足                            |
| -------------------- | ---------------------------------- | ------------------------------------ |
| 只整理文档，代码不动 | 改动少                             | 反向依赖和责任混合仍存在             |
| 单仓库显式模块       | 渐进隔离、保留交付、可执行依赖规则 | 封装依赖门禁，仍共享安装和版本       |
| 立即 npm workspaces  | 可 exports、独立测试/发布边界      | 改根、内容与部署路径，维护多个包契约 |
| 拆为独立服务         | 权限/运行隔离                      | 没有足够运行需求支撑网络和运维成本   |

## 决定

建立 Site、Book Build、Book Runtime、Publishing、Operations、Tooling 六责任模块。工程清单记录拥有关系、允许依赖、登记接口与测试，检查方向、私有入口及循环。

保留统一 package.json、锁文件和版本。Astro 固定目录归 Site，不强搬框架约定；浏览器资源地址保持，服务器旧脚本作为薄入口。每个模块有黑盒 README、设计、参考、教程、变更与测试资料。

## 后果

降低通用书构建对博客内容的依赖，发布和观测有明确边界。但目录不等于包，静态检查不证明全局对象/HTTP/DOM 的运行隔离，内部大文件仍可能多责任。

共享依赖和两条部署流程仍需协调，迁移必须同步入口与实现安装。这些后果在 [风险台账](../architecture/evolution.md) 保留，不宣称完成所有解耦。

## 再评估条件

通过 JSON 书、依赖反例、兼容入口、构建及浏览器验证维护决定；语义依赖由审查补充。出现第二真实消费者、独立版本、依赖安装压力或强制封装需求时重评 workspaces。

发布模块内部责任可以先分文件，不必等拆包；多实例 runtime 需要重新设计生命周期。改变本决定写新 ADR 并标记替代，不覆盖本记录。
