## 问题与目标

### 质量优先级

优先内容完整与可恢复，其次可维护与可诊断，再次跨设备可用，然后优化视觉与流畅性。漂亮封面不能抵消正文丢失，快速部署不能抵消无法恢复的写入。

质量不是“稳定”“易用”等形容词，应写为谁在什么条件下发出什么刺激，系统如何响应，以什么判断。

### 质量场景

| ID  | 环境与输入/刺激                                                                      | 期望响应                                            | 可判定条件与当前覆盖                                                                                                                |
| --- | ------------------------------------------------------------------------------------ | --------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |

| Q2  | Site 草稿/非法日期及 Book 配置错误类型、几何边界                                     | 合法输入通过；非法输入在对应边界拒绝                | 草稿在日期检查前过滤，非草稿非法日期抛错；Schema 错误含字段路径；不等于完整业务语义/安全验证                                        |

表中自动测试只能覆盖给定环境和输入，不证明全部场景完成。Q1 的语义目标和 Q9 的输入防护仍包含待补部分；这些是设计要求，不是将缺口改写成允许错误的理由。

性能、可用率及覆盖率门槛目前未定义：没有测量环境和基线，不写达标数字。建立目标时记录测量方法、样本、预算和责任，新增判据再关联用例。

### 人工阅读任务 Q8

从项目 README 选择任一模块，不预先阅读所有源码：

1. 找到本次变更归属和一个明确非目标。
2. 指出正确公开入口、输入输出、可能副作用和清理责任。
3. 找到一个失败条件及对应测试或明确待补项。
4. 运行该模块离线最小示例，输出与说明一致；指出完整验收还需要的命令。

四项均能准确完成才通过；把内部路径当公共 API、运行危险恢复、找不到判据或示例结果不符均失败。记录所选模块、步骤、结果和问题，不以“文档文件存在”代替任务走查。

## 范围与约束

### 约束与非目标

Astro srcDir 为 `packages/site/src`，静态集合和数据均由 Site 拥有；六个私有 workspace 包通过登记的 API 和宿主资源协作，浏览器代码由 Vite 打包。共享锁文件与独立包版本仍是协调约束；修改接口或目录时同步消费者、测试和交付清单，不保留旧脚本或服务兼容入口。

当前不建设多租户、公开投稿、完整账号系统、通用电子书发行或全自动高可用。没有基线的延迟、吞吐量、可用率和覆盖率指标不作承诺。范围扩大时重审安全、状态与成本。

## 系统上下文

### 参与者与利益

写作者需要长期保存内容、低摩擦发布并辨认修改是否成功。读者需要完整文本、清晰导航、跨设备可读及稳定链接。维护者需要低成本修改、诊断与恢复。自动化代理需要清楚的责任、授权和结束证据。

同一人可以担任多个角色，但诉求不能混淆：开发者知道某字段含义，不代表读者理解空白页，或发布者知道提交尚未上线。

### 外部边界

| 实体                    | 交互                        | 失败影响                               |
| ----------------------- | --------------------------- | -------------------------------------- |
| GitHub 仓库/API         | 版本、文件树和分支引用      | 新内容写入失败，已交付站点不一定受影响 |
| Actions                 | 验证、定时内容、产物、部署  | 新版不能正常上线，不应绕过验证补救     |
| 浏览器与字体环境        | DOM、测量、图片、触摸、导航 | 终端排版与交互异常                     |
| Lightsail/Nginx/systemd | 静态文件与 webhook 进程     | 阅读可达性或发布入口失败               |
| iOS Shortcuts           | token、文本和图片           | 协议不匹配，不能静默生成坏文章         |
| 字体与评论等资源        | 增强阅读                    | 影响需单独观察，当前不承诺全面降级     |

静态站点和 webhook 是不同运行单元。六个 workspace 包不是六个独立 container，目录图不能替代部署图。

## 模块与依赖

- 本专题按质量责任划分：Site 对内容选择和链接负责（Q2/Q5）；
- Book Build 对模型及输出负责（Q2/Q3）；
- Runtime 对实际分页负责（Q1）；
- Publishing 对写入及冲突负责（Q4/Q9）；
- Operations 对分项探针负责（Q6）；
- Tooling 对交付前门禁负责（Q7/Q8）。跨模块用例必须同时检查生产者和消费者，不能只归到发现故障的文件。

源码依赖和目录树见 [总览](overview.md)，这里不重复模块完整组织图。

## 数据与契约

- 质量断言必须区分数据单位：文章 id/collection 是来源身份；
- key 是有限哈希深链标识，不保证无碰撞；
- 物理页用于插件寻址，显示页码用于阅读。Q1 要比较分页前后文本及顺序，不能只比较页数；
- Q4 要检查一次提交内的文件树及 ref 更新，不以首页可达替代。

权威载荷字段和页码关系见 [运行契约](../reference/book-runtime-contract.md)。

## 运行与部署

- 同一质量目标需要不同环境证据。Node mock 适合 Q2/Q4/Q6 的确定性输入与失败；
- 本次 dist 检查用于 Q5/Q7 的组合；
- Chromium/WebKit 实际测量用于 Q1，但不代替 iOS。生产恢复还需核对具体提交、workflow、目标文件与浏览器内容。

这些证据是串联门槛，不是同一事务。具体执行时序见 [运行视图](runtime-and-deployment.md)，命令及记录见 [全局测试方案](../testing/strategy.md)。

## 设计取舍

### 从场景推导设计

新增主题不是只换 CSS：测量与展示必须匹配，否则溢出是内容正确性问题。新增发布格式不仅是转换：还涉及图片路径、覆盖、并发、失败恢复。目录跳转还涉及物理页和阅读页的映射。

每项功能应说明保持哪些 Q 场景、引入何种风险、证据在哪个环境有效。数字目标必须先有测量方法、环境和基线。

## 风险与验证

### 需求维护

变更设计引用已有 Q 编号或新增场景。改变范围和优先级时同步本文及 [风险台账](evolution.md)，不能通过修改测试把未讨论的质量下降合法化。

抽象层次参考 [C4](https://c4model.com/)，质量场景参考 [arc42](https://docs.arc42.org/section-10/)，具体要求由本项目定义。
