## 问题与目标

构建和测试通过后，仍需检查目标服务器的 Nginx、Webhook 进程、端口和公网入口。分散执行命令容易漏项，也难以汇总故障。Operations 用固定探针清单和统一报告记录各项结果，便于部署人员判断后续排查方向。

针对上述挑战，Operations 模块设计并实现了一组轻量级、确定性的只读健康探针（Health Probes）与报告调度体系。

模块的核心目标是在服务重启或发布部署后，以统一的数据格式执行系统级巡检，清晰汇报每一项基础依赖的就绪状态，并在发生故障时保留末次失败的 stderr、stdout 或退出码，为后续运维排查提供事实依据。

本模块定位于基础设施就绪度的只读诊断器，不承担自动化自愈或无序重试的复杂职责。

## 范围与约束

在系统责任与环境假设上，Operations 模块严格遵循以下边界约定：

1. **只读诊断**：默认定义执行只读状态探测，模块汇总数据并打印报告。注入 runner 或 command 的调用者负责控制其副作用；探针不得执行自动修复、服务重启或配置覆写。
2. **生产基准环境假设**：默认探针预设基于 Linux 操作系统、本地 9000 端口监听以及 `zhimin.ink` 公网主域名的基础拓扑，真实生产探针执行依赖系统的 Bash Shell、Systemd (`systemctl`)、文件系统权限及 `curl` 网络工具；
3. **测试隔离约束**：自动化单元测试必须通过依赖注入的虚拟执行器（`runner`）完全解耦操作系统命令，禁止在脱机测试中依赖真实宿主机的 Linux 环境变量或公网连通性；
4. **命令超时与无界等待警示**：当前底层 Node.js `child_process.exec` 调用未设置全局进程硬超时，若执行的底层系统命令发生挂起（如死锁的 sudo 交互式鉴权），探针将持续等待，调用端需具备外层看门狗保护。

## 内部组成

下图表示运行调用组成；箭头是调用关系，默认执行器通过 shell 访问操作系统，测试执行器返回内存夹具。它不表示业务模块之间的源码依赖：

```text
运维 CLI 入口 (packages/operations/src/cli/health.cjs)
           |
           v
+-----------------------------------------------------------+
| Operations 核心 API 边界 (packages/operations/src/api/index.cjs)   |
|   |-- 探针规则定义 (probes.cjs) ----> 声明默认 7 项系统检查规则 |
|   |-- 执行调度引擎 (execution.cjs) -> 顺序调用 runner 并管理重试 |
|   +-- 报告格式化层 (report.cjs) ----> 打印 PASS/FAIL 与错误文本 |
+-----------------------------------------------------------+
           |
           v
系统层执行器 (支持依赖注入)
  |-- 默认环境: 基于 child_process.exec 的系统 Shell 执行
  +-- 测试环境: 纯内存虚拟 runner 替身
```

各内部子系统的核心职责说明：

- **探针规则定义（`probes.cjs`）**：集中声明生产环境默认的 7 项巡检规则，配置每项检查的标识、标签、Shell 命令、最大重试次数、重试延迟以及输出断言函数；
- **执行调度引擎（`execution.cjs`）**：负责遍历探针队列，按序调用底层执行器，管理失败暂态重试预算，普通非零退出记录为失败项；runner 或 validate 抛错则向调用者传播；
- **报告格式化层（`report.cjs`）**：接收执行层汇总的报告，以 `PASS`/`FAIL` 标签打印清单与错误文本；
- **CLI 适配入口（`packages/operations/src/cli/health.cjs`）**：作为操作系统的命令行调用落点，解析退出状态码，并在全项通过时返回 0，存在任何失败时返回 1。

## 数据与接口

系统在执行巡检时流转的核心数据模型如下：

- **健康检查定义（`HealthCheck`）**：包含唯一标识 `id`、展示标签 `label`、执行命令 `command`，以及可选的重试次数 `retries`（默认为 0）、重试间隔 `retryDelayMs`（默认为 0ms）和自定义校验回调 `validate: ({ stdout, stderr }) => boolean`；
- **执行结果项（`HealthCheckResult`）**：包含 `{ id, label, ok: boolean, error: string }`。当且仅当子进程退出码严格为 0 且 `validate` 回调（若存在）返回真值时，`ok` 判定为 `true`；若失败，`error` 提取最新的 `stderr` 或错误描述；
- **全量健康报告（`HealthReport`）**：包含整体布尔标识 `ok`（所有检查项 `ok` 的逻辑合取）与各单项结果数组 `results`。

包根 API 只公开 `runHealthChecks()`。报告格式化由 Operations CLI 内部调用；调用者不需要也不能通过包根自行拼装探针、注入 runner 或另调打印函数。

## 关键流程

健康巡检的执行生命周期遵循线性队列轮转与暂态重试机制：

```text
启动 runHealthChecks() -> 读取探针配置数组
                            |
                            v
              遍历检查项，执行当前探针 command
                            |
              +-------------+-------------+
              |                           |
        命令返回 code=0 且验证通过    命令返回非 0 或校验失败
              |                           |
              v                           v
        记录当前项 PASS            检查当前项剩余重试次数
              |                           |
              |                   +-------+-------+
              |                   |               |
              |              仍有重试预算    重试预算耗尽
              |                   |               |
              |                   v               v
              |             等待延迟后重试  记录当前项 FAIL (保留最新 stderr)
              |                   |               |
              +-------------+-----+---------------+
                            |
                            v
                   是否还有未执行探针？
                     |-- 是: 推进到下一项
                     |-- 否: 汇聚全量 results，计算整体 report.ok
                            |
                            v
                调用 printHealthReport() 打印终端
                            |
                            v
             CLI 判定: report.ok 为 true 退出 0，否则退出 1
```

在整个执行过程中，普通非零退出或 validate 返回 false 会记录为失败并继续后续项。runner 或 validate 抛异常时，Promise 立即拒绝，后续项不会执行，CLI 捕获后输出错误并安全退出 1。

## 设计取舍

1. **严格顺序串行执行 vs. 并发多线程执行**：虽然并发探测能够缩短整体执行耗时，但多并发请求会瞬间放大服务器的 CPU 负载与网络争用，且并发打印会导致终端日志交织错乱。我们选择串行执行，确保了输出结果的按检查定义顺序与可读性。
2. **针对启动暂态设立有限重试 vs. 全局一次性断言**：Webhook 进程在执行 `systemctl restart` 后通常需要数百毫秒至数秒完成端口监听。我们在端口探针上设置了合理的重试预算（8 次重试，共最多 9 次尝试，间隔 500ms），避免了因瞬态未就绪而误报报警，同时在预算耗尽后坚决报错。
3. **只保留末次错误信息 vs. 保留全部尝试日志**：重试过程中的中间失败信息通常为常规的“连接拒绝”（Connection Refused）。报告层仅保留最后一次尝试的错误输出，使得终端排错摘要精炼聚焦，避免冗余刷屏。

## 失败与边界

开发与线上运维时需重点关注以下异常边界与行为表现：

1. **服务非 Active 状态**：若 Nginx 或 Webhook 服务未处于运行态，探针将标记为 `FAIL`，运维人员应登录机器核对 `journalctl -u blog-webhook.service`；
2. **环境变量文件权限或缺失**：若探针检测不到目标环境变量文件，说明部署配置未完成同步，需比对生产环境的 `.env` 声明；
3. **公网缓存与旧版本遮蔽**：当前公网探测只断言 curl -fsS 的退出码为 0，正文被丢弃，不检查精确状态码、正文或部署版本，若 CDN 或 Nginx 缓存了旧版本静态文件，探针依然会通过，真实版本一致性需额外校验构建哈希；
4. **排错与环境恢复**：探针失败本身不具有破坏性，运维人员根据报错信息修复配置或重启服务后，重新执行 `node packages/operations/src/cli/health.cjs` 即可重新验证。

## 验证与演进

当前自动测试使用内存 runner：

- **逻辑单元测试**：`packages/operations/tests/server-health-check.test.mjs` 在内存中注入虚拟 runner，验证默认清单完整性、失败结果聚合、启动暂态重试成功；预算耗尽、runner/validate 抛异常和输出回退规则尚无专门用例；
- **契约完整性测试**：`tests/integration/service-api.test.cjs` 检查公共入口存在、导入不执行服务，以及 canonical 服务模板路径；没有验证全部函数参数语义。
- **CLI 生命周期测试**：`packages/operations/tests/cli.test.mjs` 使用报告及执行 API 替身验证真实 CLI 的打印、成功/普通失败退出码和异常退出；不执行默认 runner，也不补足默认探针的预算耗尽覆盖。

未来演进规划：若后续引入多节点集群部署，可在执行层引入单探针可配置的硬超时机制（`timeoutMs`）；针对公网连通性探针，可扩展支持针对 HTML 响应头中 ETag 或部署 Commit 哈希的版本一致性精确校验。
