## 目的与范围

约束自动化编程助手的任务范围、读取、修改、验证和交付。代理不得把诊断授权当作实施授权，也不得把本地修改当作部署授权。
核心原则包括：

1. **明确角色定位**：代理是系统架构调研、代码编写与测试验证的技术协作者，而非默认的运维管理员或发布操作员；
2. **授权最小化准则**：代理的行动空间严格限定于用户自然语言指令明确划定的范围与项目既定工程规范内；未经用户显式授权，任何本地代码修改均不代表获得了 `git push` 推送、生产环境服务拉起/重启、外部消息发送或公网资源修改的授权；
3. **安全红线原则**：诊断与分析任务默认以只读模式执行；任何涉及磁盘写入、配置覆写或文件删除的动作，必须具备明确的变更意图与可执行的回滚方案。

本规范适用于所有主流编程代理（如 Antigravity CLI、Codex 等）在本工作区内的执行行为。

## 规则与要求

### 1. 引导文件职责分工

- **外层工作区 `AGENTS.md`**：只说明项目根在 `blog/`、命令执行目录及项目规则位置，不复制项目规则或共享规范；
- **项目根 `blog/AGENTS.md`**：项目代理执行规则的唯一入口，说明必读资料、模块边界、安全限制、验证命令与交付要求；详细规则链接至本规范和其他共享规范，不再建立单数文件、别名或跳转文件；
- **`docs/guides/contributing.md`**：面向维护者和贡献者，说明任务输入、变更流程、验收与恢复；不作为另一份代理执行规则；
- **各子模块 `README.md`**：各独立模块的局部准则与技术栈约束收敛在模块根目录下，不向全局 `AGENTS.md` 泛滥倾倒局部细节。

### 2. 上下文获取与工作区尊重

- **先读规范再行动**：代理在接收到任务指令后，必须首先读取全局 `README.md`、`docs/guides/contributing.md` 以及目标模块的设计与接口参考，全面理清系统边界后再行动；
- **尊重既有脏工作区（Dirty Worktree）**：执行 `git status -s` 时，若发现工作区已存在未提交的修改，必须保持最大的谨慎，严禁执行 `git reset --hard`、`git clean -f` 等破坏性指令覆写用户的已有劳动，修改必须严格限制在当前任务授权的局部文件内；
- **严禁凭空臆测**：对于模糊的技术事实或未记录的协议，必须以真实源码、配置定义与一手官方规范为依据，不确定的内容必须明确标注为待定假设，严禁编造虚拟的 API 或外部支持。

### 3. 安全防护绝对红线

- **绝对凭据保护**：严禁以任何理由读取、打印、修改或提交工作区根目录下的私钥文件（如 `LightsailDefaultKey-*.pem`）或生产环境变量中的 Secret Token；
- **禁止私改上游原件**：严禁手动修改 `public/vendor/` 或 `turnjs4/` 等第三方只读依赖源码；
- **禁止降低门禁标准**：严禁通过注释测试用例、删除断言、放宽数值容差或在 Linter 中添加全局 disable 来强行伪造“门禁通过”。

## 执行流程

代理在处理用户请求时，必须严格执行四步标准闭环：

### 阶段一：开工准备（只读分析）

1. 确认当前执行目录位于受版本控制的项目根（`blog/`）；
2. 执行 `git status -s` 查看工作区现状，记录已存在的未暂存文件；
3. 读取目标模块的设计说明与接口参考，确立任务边界与核心交付物。

### 阶段二：方案设计与反例构造

1. 梳理变更影响面，识别受影响的上下游消费者与文档引用；
2. 若涉及业务逻辑修复或扩展，优先构造失败测试用例，证明原缺陷确实存在；
3. 若需外部写入或不可逆操作，立即停止并向用户报告具体风险，请求明确的方向授权。

### 阶段三：编码实施与闭环验证

1. 在授权目录内实施改动，同步更新公共接口、JSDoc 注释与受影响的配置文件；
2. 若修改了配置 Schema，立即执行 `npm run docs:generate` 同步派生文档；
3. 执行模块本地测试，确认新测试用例全部 PASS；
4. 执行全仓门禁命令 `npm run verify`，确保类型、边界、Lint 与文档检查全部绿灯。

### 阶段四：规范交付与状态汇报

1. 审查 `git diff`，确认所有变动均在授权范围内，无意外的文件污染；
2. 交付汇报中必须明确区分“本地代码已就绪”与“生产线上已生效”，详细列出执行的具体命令、退出码以及未执行的真实部署项，严禁夸大交付事实。

## 正反例

### 合格协作范例

代理在处理 Webhook 提交流程修改时：

- **动作**：阅读 `packages/publishing/docs/` 下的契约，使用内存数据与虚拟 request 替身完成测试，确认当 GitHub API 冲突时系统能正确返回 400 且 `force: false` 安全参数生效；
- **汇报**：“已在本地通过全套替身测试，验证了冲突拦截与原子提交流程。因未获得服务器凭据与生产操作授权，本次未向真实 GitHub 发起任何写入，未在生产服务器执行重启。”

### 不合格典型反例

- **反例一：越权盲目操作**：本地单元测试刚通过，代理便自动推测并擅自执行 `git push origin main` 或尝试 SSH 登录生产服务器；
- **反例二：破坏性重置工作区**：看到工作区有其他文件的未暂存修改，直接执行 `git checkout .` 导致用户未保存的代码彻底丢失；
- **反例三：虚假完成汇报**：“代码已修改完毕，生产服务器已完全恢复正常运行”——实际上仅在本地修改了两个函数，从未登录过服务器。

## 例外与限制

1. **阻塞报告规范**：当代理遇到缺少必要设计决策、环境依赖缺失或缺少操作权限时，必须输出结构化的阻塞报告，明确说明当前已完成的本地事实、受阻的具体命令/文件、产生原因以及需要的明确方向，严禁陷入无意义的循环重试；
2. **多代理并行限制**：在当前环境未显式启用多智能体编排时，不得自行假设或虚拟并行角色，任何并行分派必须由具有集成者职责的角色负责最终的 Diff 审查与全仓回归。

## 检查与验收

代理在提交工作前，需对照以下标准自检：

- [ ] 工作目录严格位于 `blog/`，未在工作区外部产生临时脏文件；
- [ ] 根目录下的私钥文件与生产 Token 未被任何工具或命令读取；
- [ ] 历史既有的未提交改动被完整保留，无意外覆写；
- [ ] 自动化门禁测试全部退出 0，无忽略的断言失败：
  ```sh
  npm run verify
  ```
- [ ] 交付报告清晰说明了可观察的技术事实、修改范围、测试证据与剩余的已知限制。
