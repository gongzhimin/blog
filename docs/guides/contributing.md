## 目标与适用条件

### 贡献的目标

一次贡献应改善用户或维护者的问题，同时保留必要的内容、契约、兼容与恢复能力。代码可运行是必要条件，设计正确、证据有效和资料可维护同样是交付的一部分。

不要求每个小改动写大型设计；要求任何人都能说明为什么改、影响哪里、怎么证明，以及出了问题如何退出。

## 前置条件

### 修改前的准备

1. 确认任务授权及当前 worktree，保留已有改动，不擅自推送或部署。
2. 阅读 [系统架构](../architecture/overview.md)、目标模块 README、设计、接口和测试策略。
3. 确认本次是内容、局部实现、契约/状态、还是部署与安全变更；按 [变更规范](../standards/change-management.md) 选择证据。
4. 写可观察的验收条件和非目标。涉及边界、数据或权限时先设计，不先搬目录或扩大接口。

Node 22 LTS >=22.13 或 24+，使用 npm ci 安装锁文件指定依赖。开发练习见 [入门指南](getting-started.md)。

## 输入与配置

开始前列出本次输入：需求和验收条件、受影响模块、现有失败案例、当前工作区差异。

模块归属与公开入口以 [模块清单](../../packages/tooling/src/modules.json) 为准；配置变更分别读取 Book Schema、Site 字段契约及当前 JSON，不把生成参考当作可编辑来源。

给代理分配任务时，明确任务类型、范围、非目标和验收条件。例如：

> 调整传统目录窄屏显示上限，仅修改 Site 的相关配置、校验及文档；书籍首页行为不变。补充边界值测试，执行 verify 和浏览器布局验证，不提交或部署。

解释或诊断不自动授权修改，实施不自动授权外部写入。代理执行要求以 [AGENTS.md](../../AGENTS.md) 为入口。

确认本地 Node 满足 `package.json` engines，依赖版本来自 `package-lock.json`。涉及协议时记录调用方、字段、错误和兼容条件；涉及部署时记录目标环境、提交及恢复版本。

真实凭据只通过批准的环境或服务配置提供，不写入示例、测试 fixture 或交付记录。

## 操作步骤

### 设计和实现

小改动可在任务/交付说明中记录判断；跨模块、协议、生命周期和安全变化写 docs/changes 下的设计。需要长期保存的选择写 ADR，说明替代方案及后果。

- 行为修改先建立能复现原缺口的测试，观察失败原因，再实现并回归。重构保护明确的业务不变量；
- 经授权可修改接口及路径，同步调用方并删除旧入口，不建立转发层；
- 新功能同步模型、校验、配置说明和测试。不能因“机器检查过了”省略责任及失败分析。

按 [代码及注释规范](../standards/code-and-comments.md) 编写接口与维护约束；按 [文档规范](../standards/documentation.md) 选择资料类型。

没有文档影响时说明判断依据，而不是机械改所有文件。

## 结果核对

### 验证

先格式化本次实际修改的文件，再运行完整门禁；`npm run format` 会写整个配置覆盖范围，脏工作区不要不经核对直接全量执行。

例如本次只修改 README 和文档规范时执行以下命令；其他任务换成自己的实际文件列表，不顺带格式化无关文件。

```sh
npx prettier --write README.md docs/standards/documentation.md
npm run verify
```

配置定义/生成来源改变时先运行 npm run docs:generate。浏览器运行时、布局、字体、图片、翻页和触摸改变时，在构建后运行 npm run test:e2e。发布、健康检查或门禁变化还需执行对应模块测试。

交付候选运行 `npm run verify:release`：包含完整门禁、实际 tarball 隔离消费/类型编译与 Chromium。隔离安装允许从 npm 获取缺失依赖，禁安装脚本，不链接原仓库 node_modules；网络或缓存不足是未通过，不跳过。不得以各包局部 test 替代递归盘点与零跳过门禁。

私有包版本：先 `npm run changeset` 登记受影响包，再查看 `npm run version:status`；经审查执行 `npm run version:packages`，同步锁文件后重跑验收。包版本独立，消费者的精确依赖随生产者变化更新；不运行 publish、不创建 registry tag。

每条命令记录版本、环境、退出码和失败范围。不要删除测试、削弱断言、广泛关闭检查或使用 npm audit fix --force 来制造通过。检查故障先区分实现、测试、环境和设计问题。

### 两轮审查

先审查需求与设计：行为是否解决正确问题，模块和权限是否合理，是否额外扩展范围。再审查实现及证据：接口、失败、兼容、测试有效性和文档是否一致。

文档改动也要经过事实核对与读者任务走查；字数、标题或链接存在不是质量结论。审查问题按必须修复、建议、信息区分，重要问题未解决不能宣称完成。

## 失败与恢复

验证失败保存首个诊断、命令、环境和退出码。格式或生成漂移先核对本次输入；类型、构建和测试失败定位责任模块。不得删除测试、降低断言或扩大排除范围来取得绿灯。`verify` 使用串行短路：前面失败后，后续阶段是未执行，不是通过。

修正后重跑受影响的局部检查和完整门禁。需要撤销时只回退本次明确改动，保留已有工作区修改，不整仓库重置；内容写入、机密轮换及生产回滚需单独确定目标和授权。

交付说明包含问题、最终行为、责任影响、实际命令和退出码、兼容/恢复及剩余限制。未运行的验证不能引用上次结果代替本次证据。

本地实现不自动授权 commit、push、服务重启或上线。CI 的验证/部署定义不代表实际运行已通过。发布另行按 [部署指南](../operations/deployment.md) 执行，明确目标提交、产物和线上核对结果。
