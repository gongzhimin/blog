# 设计导向的工程文档体系

## 范围

重写六模块所有自写文档及根当前工程资料。读者为项目维护者、设计审查者和贡献者。保留历史和生成文件，不为了增加长度修改历史；现有专题资料整理定位并链接权威设计。新增资料不改变运行逻辑或扩大部署授权。

## 实施记录

### 问题与目标

上一轮建立了目录和检查，但核心文档没有回答系统为何存在、质量要求如何影响架构、模块边界为何成立，以及设计如何验收。文件齐全不能证明设计完整。本轮以维护者能在不先读源码的情况下作出合理变更决策为目标。

### 方案取舍

只加长现有短文，仍会保留重复和缺乏论证的问题；严格照搬大型企业模板会产生空章节和不适用的审批。本轮选择按读者问题分层，并裁剪 arc42 的架构视角、C4 的抽象层次、Diátaxis 的文档类型。依据只是设计方法，项目不宣称满足完整国际标准。

### 信息架构设计

根 README 负责定位和阅读路线。architecture 提供系统概览、上下文和质量场景、运行与部署视图、风险及演进。standards 定义设计约束及工程制度。模块 explanation/design.md 回答问题、边界、模型、协作、失败、取舍、演进；reference/api.md 提供精确契约，不与设计混写。tutorials 是有明确结果的练习，guides 是带风险和检查点的变更步骤，testing 将风险映射为证据。

单一事实来源：配置当前值来自配置和生成参考，源码负责当前实现，需求与规范负责应有约束，ADR 负责选择理由，变更记录负责时点证据。发生冲突先诊断，不把代码自动视为正确需求。

## 验证证据

逐项审查设计文档是否有目标、非目标、职责、模型、不变量、交互、错误、权衡和演进触发条件；规范是否有规则理由、范围、正反例、例外和验证；操作资料是否有前提、步骤、成功表现及失败处理。检查相对链接、生成漂移、格式及完整项目验证。验收结果见 [交付记录](completion.md)。

理论依据：[arc42](https://docs.arc42.org/home/)、[C4](https://c4model.com/)、[Diátaxis](https://diataxis.fr/)、[Google review](https://google.github.io/eng-practices/review/reviewer/looking-for.html)。

## 剩余限制

源码审阅若发现问题，作为已知风险记录，本轮不擅自引入代码重构。具体项目判断需以当前仓库证据支撑。
