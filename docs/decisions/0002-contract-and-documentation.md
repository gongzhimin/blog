# ADR 0002：契约来源与设计文档分层

状态：接受于 2026-10-03；2026-10-04 补充文档深度与来源原则。读者：契约维护者、设计审查者。

本记录保存当时完整决定；目录、旧入口、Schema中转和重定向策略已由 [ADR 0004](0004-physical-modules-and-public-api.md) 替代。当前实现以新决定和模块API为准。

## 背景

配置定义、手写校验和手写参数表独立维护，会出现同字段不同范围；历史尺寸又容易被当成当前值。只有目录完整的文档无法解释目标、模型和取舍。

需要同时处理可机器验证的一致性与不可由工具证明的设计知识，不能用生成 API 文档替代架构设计。

## 备选方案

手写全部资料灵活但漂移风险高；从代码生成全部资料精确却不包含需求和选择；混合来源分层维护既能保持结构契约又保留论证，代价是必须明确权威和人工审查。

## 决定

Book 结构定义集中在模块 Schema，由 Ajv 执行，旧编辑器路径引用它。首页编辑器 Schema 与配置参考从运行字段定义及描述生成；跨字段业务规则仍由运行校验负责。

核心模型使用显式 JSDoc 来源和限定类型检查。参考由定义与当前值生成并验证漂移；设计从问题、质量、模型、协作、失败、备选及演进出发，不以函数列表为主线。

文档按读者用途区分设计解释、精确参考、学习练习、操作步骤和测试策略。共享制度集中，AGENT/AGENTS 通过链接分工，历史显式标状态。

## 后果

结构一致性更容易检测，但类型覆盖不是全仓严格模式，Schema 不是全部语义校验，模块存在和链接通过不等于设计完整。自然语言、运行协议及浏览器排版仍由事实审查、任务走查和行为证据维护。

生成输出引入格式工具依赖，修改来源必须重新生成。不能手改表格解决漂移，也不能自动将现有代码视为正确需求。

## 再评估条件

验证非法输入、生成漂移、模块文档和依赖反例；设计质量用读者任务与规格审查验证。扩大参数或内容源时重新核对来源。需要全仓类型或新的文档平台时单独评估成本，不以工具引入代替内容质量。
