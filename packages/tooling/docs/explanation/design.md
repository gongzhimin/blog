## 问题与目标

维护者需要及时发现三类漂移：代码绕过模块公开入口，文档结构或路径与工程约定分叉，配置参考落后于来源。Tooling 把可机械判断的规则集中成可重复检查，让本地与 CI 对同一工作区给出一致诊断。

成功条件是违规样本被拒绝、合法对照被接受、派生产物与来源一致。它不替代接口审查和读者走查，文档内容是否正确仍由所属模块维护者负责。

## 范围与约束

清单权威是 `packages/tooling/src/modules.json`。

CLI 扫描 src、public、docs 和项目 README/AGENTS，排除 vendor、构建缓存、历史原件与旧计划正文；Site 内容文章不参与工程文档检查，归档和旧计划索引仍受检查。

src 包含模块内 CLI、配置及局部测试，边界检查也扫描这些源码。根 tests 的跨模块集成夹具不作为应用依赖图节点；它们通过 Node/Playwright 执行和全局测试策略验收，不能因此成为应用导入私有实现的通道。

- 依赖检查使用 TypeScript 的语法树，不执行被检查源码。Astro 以正则提取 frontmatter 和 script 后分别解析；
- 模板表达式不在完整覆盖范围。API 输入由调用者提供，文件访问与子进程由 CLI 拥有；
- 普通生成模式会写文件，不能把整个模块称为无副作用。

## 内部组成

下图表示实现责任和调用方向，箭头不是源码中的业务依赖授权：

```text
+---------------------+     +-----------------------+
| public API           | --> | cli/verify.mjs         |
| inspectRepository    |     | 检查/聚合/进程状态      |
+---------------------+     +-----------+-----------+
                                       |
                         +-------------+-------------+
                         |                           |
                         v                           v
              +--------------------+     +--------------------+
              | internal/checks.mjs|     |internal/documents.mjs|
              | 清单/依赖/链接/表格 |     | 元数据/章节/归属/父图 |
              +--------------------+     +--------------------+
+------------------------+    +----------------------------+
| cli/generate-reference | -->| Book Schema/Site API/配置  |
| 排版/比对/写入          |    | 来源由业务模块维护          |
+------------------------+    +----------------------------+
```

- checks 中的 owner 用 owns 查找归属，TypeScript 遍历导入节点；
- documents 使用 js-yaml 解析元数据并核对固定章节。verify 负责文件是否存在、必备文档、id 唯一以及整仓关系；
- generate-reference 负责两份 Markdown 与首页编辑器 Schema。不存在另一个清单模型或独立边界分析器文件。

## 数据与接口

模块定义包含 id、root、owns、dependencies、entries、tests 和可选 applicationEntries；允许边不能代替公开入口登记。owns 仅为本模块 root/；CLI 登记在本模块 cli/，不能借此认领其他目录。

跨模块相对导入必须同时满足 dependencies 和目标 root/api/ 中 entries 的精确路径。

元数据有 id/type/status/created/modified/scope/owner/parent/related 九字段。parent 是一个主要上位文档，related 是关联目标数组。局部函数不检查所有目标存在，CLI 负责组合这些条件。

包根仅公开 `inspectRepository({ root, mode })`，把静态检查子进程及其输出收敛成一个报告。生成参考是写入型工作流，继续由 `npm run docs:generate` 显式触发。检查器、元数据解析和规则表是包内实现，调用者不需要逐个调用并汇总。

## 关键流程

下图表示进程与产物状态。API 的局部规则检查和仓库扫描承担不同责任：

```text
+--------------------------+
| verify docs/boundaries/all|
+-------------+------------+
              |
              v
+--------------------------+
| 读 modules.json + 扫文件  |
| 清单错误加入 diagnostics |
+-------------+------------+
              |
       +------+------+
       |             |
       v             v
+-------------+  +---------------------+
| boundaries  |  | docs                |
| 逐文件 AST   |  | 元数据/链接/父图     |
| 检查导入边   |  | 配置校验 + 生成比对 |
+------+------+  +----------+----------+
       |                   |
       +---------+---------+
                 v
      +-----------------------+
      | 有诊断: stderr/退出 1 |
      | 无诊断: stdout/退出 0 |
      +-----------------------+

来源 --> 生成内容 --> Prettier --> 与现有目标比较
                                  |
             +--------------------+-------------------+
             |                    |                   |
             v                    v                   v
       --check: 不写       --patch: 输出补丁      普通: 写目标
       漂移退出 1          调用方审查/应用        逐文件写入
```

- 清单规则诊断通常聚合后报告；
- 读取、JSON 解析或配置校验异常可提前终止。生成逐目标处理，没有事务回滚；
- 中途失败可能留下部分更新。CLI 不自动重试。npm verify 是 package.json 中串行短路门禁，不能从本图推导前阶段失败后仍执行全部检查。

## 设计取舍

选择 TypeScript AST 而非直接查找 import 字样，使注释和普通字符串中的示例不当作依赖节点。成本是解析器依赖，以及仍需明确处理 Astro 提取和模块解析差异。require 按名称识别而不分析作用域，不能保证所有形式都没有误报。

选择显式清单与精确 API 文件登记，让模块作者承担公开契约维护成本；不自动把目录相邻或文件存在视作允许调用。相对路径不补扩展名和 index，规则简单可复核，但不能代替 Node/Vite 的真实解析。

生成内容经 Prettier 后比对，使排版固定。来源更新后必须重新生成并审查；日期保留最近内容变更，不用每次运行刷新日期掩盖漂移。表格只展开 properties 等有限字段，不复制完整 Schema 校验能力。

## 失败与边界

计算型 import/require 被拒绝，项目别名采用拒绝策略，外部包内部依赖不扫描。路径不 realpath、不跟踪符号链接；静态图通过不证明 HTTP、数据岛或全局脚本协议兼容。

文档检查保证有限结构。危险 shell 示例及旧清单路径采用风险模式检测，不能证明 shell 语义安全，也不能判断设计是否充分；合法标题与非空正文不是内容质量结论。链接规则不验证外链可达、全部 Markdown 语法或页内锚点。

生成漂移先检查来源与本次差异，再决定是否生成；不得自动扩大依赖或恢复整个目录。规则误报需要合法对照和最小反例，不能只添加白名单压过错误。

## 验证与演进

扫描范围以实际 workspace 为准：源码来自 `packages/<name>/src`，当前文档来自包目录和根 docs，Site 的文章内容不按工程文档检查。CLI 从目标 root 读取模块清单及 package manifests；包名导入同样受依赖方向和根入口约束。

测试门禁独立于 inspectRepository 的静态模式：test.mjs 递归盘点测试并比对清单，Node 运行后拒绝空集、失败、取消、跳过和 TODO；Playwright 报告器拒绝动态跳过、预期失败和重试。完整验收仍由根 verify / verify:release 编排。门禁变更要用真实布局违规注入和实际执行器退出码回归，不能只测字符串分析函数。

[测试方案](../testing/strategy.md) 将实际测试文件与输入/预期配对。局部 API 样本、CLI 扫描、生成漂移和完整门禁各自提供不同证据；完成报告记录实际运行和未运行项。

新增语法、别名解析或模块类型前，先建立合法/非法对照与误报案例；复杂度和失败传播变化同步 [算法](../algorithms/module-dependencies.md)。

若要统一诊断或事务写入，应先说明调用者需求、兼容成本及失败恢复，而不是把未来能力写成现状。
