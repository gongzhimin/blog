## 目的与范围

约束仓库当前工程 Markdown：项目入口、共享架构与协议、模块 README、设计、算法、接口、教程、操作指南、测试方案和规范。文章正文、第三方原件及归档原文不套用当前章节模板。

本文是文档规则的权威来源；[检查器](../../packages/tooling/src/api/index.mjs) 实现其中可机械判断的部分。修改模板必须同步检查器及正反例测试，不能通过修改检查器降低未讨论的内容要求。

规则属于本项目，不宣称通过国际标准认证。

设计文档回答问题、边界、选择与后果；接口文档回答怎样正确调用；教程带读者完成练习；操作指南解决已经明确的任务。不得用一种文档替代另一种。

## 规则与要求

### 技术语言与排版

- 必须明确主语、条件、动作和结果；涉及数量写单位，涉及成功写判定条件。
- 当前行为、强制规则、建议和未实现能力分别写清。使用“必须”表示验收要求，“建议”允许有依据地选择替代做法。
- 不用“完全解耦”“绝对可靠”“100% 精准”等词代替边界说明。删除没有增加条件、证据或取舍的引言和重复总结。
- 一个文件只有一个 H1，同类型 H2 顺序固定；细分主题使用 H3。标题前后留空行，代码块标明语言，接口名、路径和字段使用行内代码。仓库文档链接使用相对路径，不使用机器本地 file URL。
- 中文与英文术语之间留空格；保持 API、JSON、DOM 等标准名称，不给同一概念轮换名称。
- 一个段落只回答一个问题；前提、行为、结果、限制和后续操作不要堆在同一大段中。主题或适用条件改变时用空行分段，不能只在源码里折行而让渲染后仍是一段。
- 并列职责、输入字段、约束、错误分支和关联资料用无序列表；有先后依赖的操作用有序列表；同字段比较用表格。不要用连续分号或顿号把完整规则挤成一行，也不要将连续因果论证机械改成清单。
- 列表前保留空行。每项说明一个可独立核对的条件或结论；多段列表内容缩进到同一项，必要时使用二级列表，不把不同步骤合并到一个条目中。接口签名与参数表仍保留代码和表格形式。
- 所有当前工程文档都在 H1 后、第一个 H2 前提供目录，不再按行数区分短文和长文。目录使用独立的“目录：”引导行、一个空行和无序列表；每个 H2 占一项，名称和顺序与正文一致。
- 目录采用原生 Markdown 页内链接，不新增 H2，不使用渲染器专用指令，不用中点、分号或一行多个链接压缩目录。默认只列 H2；H3 的导航在所属章内组织。
- 生成资料由生成器维护相同目录格式，不手工改派生内容。历史原件保留原格式，不参与当前目录统一。

### 统一元数据

当前 Markdown 必须以 YAML frontmatter 开头，严格采用以下字段顺序。字符串加引号；parent、related 使用仓库根相对路径，不包含凭据、绝对路径或上跳路径。

```yaml
---
id: 'book-build-pagination-example'
type: 'algorithm'
status: 'draft'
created: '2026-10-04'
modified: '2026-10-05'
scope: 'book-build'
owner: 'Book Build 维护者'
parent: 'packages/book-build/README.md'
related: ['docs/standards/documentation.md']
---
```

| 字段     | 必填和取值                                           | 更新规则                                                                                |
| -------- | ---------------------------------------------------- | --------------------------------------------------------------------------------------- |
| id       | 是；仓库唯一的小写字母、数字、连字符标识             | 文档身份不变时保持，包括迁移、改模板、改标题；不同责任的新文档分配新 id                 |
| type     | 是；下述主类型或辅助类型                             | 按读者任务选择；模块目录必须与类型匹配                                                  |
| status   | 是；draft / active / deprecated / historical         | draft 未完成核对；active 当前有效；deprecated 保留但不推荐的旧契约；historical 时点记录 |
| created  | 是；有效 YYYY-MM-DD 日期                             | 当前文档身份首次建立日；迁移和改模板不重置，不表示每轮整改或文件复制时间                |
| modified | 是；有效日期，不早于 created                         | 实质内容、关系、状态或章节变更时更新；仅排版或无变化检查不刷新                          |
| scope    | 是；模块使用清单 id 或 root，全局写明确工程/协议范围 | 范围改变时同步责任、正文和归属                                                          |
| owner    | 是；实际维护角色                                     | 表示核对和更新责任，不复制 Git 作者名单，不虚构负责人                                   |
| parent   | 是；一个上位文档路径                                 | 根 README 可以自指；其他 parent 图无环，模块专题的 parent 留在本模块                    |
| related  | 是；文档或权威实现路径数组，可为空                   | 只登记直接相关事实源，不复制正文所有链接；移动目标时同步更新                            |

created 无可靠旧记录时，首次正式建立当前文档身份的日期可以作为起点，不推测更早日期；建立后固定。active 不证明内容已与源码同步，modified 不证明验证通过。

具体作者和改动保留在 Git，实际审查和执行证据保留在变更记录，不另维护手写版本号、提交号或评审人数。

字段语义参考 DCMI 的 identifier、type、created、modified、isPartOf 和 relation；status、scope、owner 为项目字段。日期使用 RFC 3339 full-date 形式。

### README：独立理解模块

H2 按下表顺序，读者不先读源码也能找到调用和验证方式。

| 章节         | 必须包含                            | 合格条件                               |
| ------------ | ----------------------------------- | -------------------------------------- |
| 用途与边界   | 服务对象、解决的问题、非目标        | 能判断任务是否归本模块                 |
| 能力与限制   | 支持的输入和结果、当前缺口          | 未实现能力不写成保障                   |
| 内部结构     | 实际目录树、各部分责任              | 路径存在，API 与私有实现分开           |
| 依赖与数据流 | 上下游、箭头含义、共享契约          | 源码依赖与 HTTP/文件关系不混用         |
| 主要接口     | 入口、输入、输出、环境、副作用摘要  | 能选择正确入口，完整字段链接到唯一参考 |
| 最小使用示例 | 前置环境、命令或调用、观察结果      | 从声明目录可执行，不需要真实生产凭据   |
| 配置         | 来源、默认/覆盖、读取时点、权威位置 | 不手写复制整份生成参数表               |
| 测试与验证   | 局部和集成命令、证明范围、限制      | 不用永久测试总数替代证据               |
| 文档导航     | 设计、算法、接口、教程、指南、测试  | 当前路径正确，无旧路径跳转页           |

### architecture：系统设计

| 章节       | 必须包含                         | 合格条件                           |
| ---------- | -------------------------------- | ---------------------------------- |
| 问题与目标 | 用户问题、质量场景及成功判据     | 目标可以对应测试或人工任务         |
| 范围与约束 | 非目标、运行环境、信任边界       | 限制说明来源和影响                 |
| 系统上下文 | 使用者、系统边界、外部实体和交互 | 图的范围及外部故障影响明确         |
| 模块与依赖 | 职责、源码依赖、真实组织树       | 依赖以清单为准，模块不当作独立进程 |
| 数据与契约 | 核心术语、不变量、单位、权威协议 | 不把序列化边界等同于全对象不可变   |
| 运行与部署 | 构建、浏览器、服务和交付顺序     | 标明进程、产物、失败点和成功边界   |
| 设计取舍   | 至少一个实际备选、选择条件和成本 | 不用“更先进”代替依据               |
| 风险与验证 | 风险、已有证据、缺口、重审触发   | 未测设备/指标明确写为未验证        |

总览必须包含系统上下文图、源码依赖图、目录图和运行/部署图。专题保留同一章节顺序，但只展开本专题的责任、关系和场景；公共组织图链接到总览，不复制一套易漂移内容。不适用章写明原因和对应的权威位置，不能只放“详见”。

| ---------- | ------------------------------ | -------------------------------------- |
| 问题与目标 | 独立责任和判据                 | 从需求出发，不以源码文件清单开头       |

### algorithm：算法设计

| 章节       | 必须包含                             | 合格条件                               |
| ---------- | ------------------------------------ | -------------------------------------- |
| 问题定义   | 要解决的问题、成功判据和非目标       | 不仅描述某个函数做什么                 |
| 输入与输出 | 类型、字段、单位、前后条件           | 空输入和非法输入有定义                 |
| 数据结构   | 字段、关系、不变量及状态             | 结构支撑步骤，不只列变量名             |
| 算法步骤   | 有序步骤或伪代码、实现定位           | 读者可以手动推演一个案例               |
| 边界与失败 | 空值、极值、异常、终止与恢复         | 区分正常停止和失败退出                 |
| 复杂度     | 变量、时间、空间和假设               | DOM 布局/网络成本单列，不能只写 O(n)   |
| 正确性依据 | 不变量、进展、终止及不保证的部分     | 条件不足时不宣称完整证明               |
| 测试案例   | 具体输入、独立预期、用例名、覆盖状态 | 正常/边界/失败各有案例；待补不伪装已测 |

### interface：接口和协议参考

| 章节         | 必须包含                         | 合格条件                          |
| ------------ | -------------------------------- | --------------------------------- |
| 适用范围     | 调用者、环境、协议边界           | 区分 Node、Astro、浏览器及 HTTP   |
| 接口清单     | 完整公开导出、签名或方法/路径    | 与清单 entries 和实际导出核对     |
| 输入与配置   | 类型、单位、缺省、校验、读取时点 | 调用者可以构造合法输入            |
| 输出与副作用 | 返回、I/O、状态变化、资源所有权  | 同步/异步、共享引用、清理责任明确 |
| 错误与边界   | 错误类型/状态码、部分成功、极值  | 返回码不能推导出的结论明确        |
| 兼容与示例   | 最小调用、加载顺序、变更约束     | 示例可执行，旧协议是否支持清楚    |
| 验证与关联   | 契约用例、权威定义、相关设计     | 不以导出名存在代替行为验证        |

HTTP 参考必须写出鉴权所在位置、请求和响应示例、状态码含义、超时结果不确定性及重试条件。配置参考区分 Schema 约束、主题默认和当前实例值。生成参考不是完整 API 或设计说明。

#### API 参考的条目格式

API 参考按公开入口和导出符号组织，不按实现文件或执行时间线组织。页面开头先给最常见任务的入口选择与一个最短可运行示例；随后提供完整导出清单，再按导出符号逐项说明。不要把“怎么完成一个任务”的教程步骤复制到每个函数条目。

每个函数、组件、类型和资源入口必须使用同一条目模板：

1. **签名**：展示从 package exports 可调用的名称、参数和返回类型。若类型由声明文件表达，声明文件与参考必须一致。
2. **作用**：用一句话说明调用者可观察到的结果；实现背景只有影响调用方式时才写。
3. **参数**：逐参数表列名称、类型、必填性、默认值、单位/允许值及调用者责任。对象参数需要逐字段列出；不能只写“配置对象”。
4. **返回值**：说明返回结构、同步/异步、字段含义，以及对象是新建、浅/深复制还是共享引用。无返回值明确写“无”。
5. **错误与副作用**：按可观察条件列出抛出的错误/拒绝原因、I/O、全局注册、DOM、进程状态或资源清理责任。不得将所有输入错误笼统写成“可能失败”。
6. **示例**：仅在帮助调用者消除歧义时提供；示例注明执行环境、必要前置条件和可观察结果。页面顶部保留一个端到端短例，避免每个相邻条目都重复完整搭建流程。

参数和返回值中若类型足以表达结构，正文不重复抄完整字段定义；改用链接到唯一模型定义，并在本条目解释与调用相关的默认、约束、所有权和失败行为。类型/Schema 是结构事实来源，API 文档是调用行为事实来源。源代码 JSDoc/TSDoc 应描述每个公开符号及其参数、返回和有意义的异常；可以生成参考或做一致性检查，但不能用自动生成替代契约审查。生成器输出不可手工编辑。

对于没有稳定异常类型的 JavaScript API，只记录源码明确抛出或可由依赖稳定观察到的错误条件；对无法保证的异常应写“回调/依赖异常原样传播”，不要伪造精确异常类。安全、HTML/CSS 信任、时区、文件访问、碰撞、重试及兼容性等限制放在相关接口条目，不能只藏在页面末尾。

这些规则综合了 [Diátaxis Reference](https://diataxis.fr/reference/) 的信息导向、产品结构组织和固定模式原则，[Google API reference comments](https://developers.google.com/style/api-reference-comments) 对公开成员、参数、返回和异常的逐项要求，以及 [TypeDoc Doc Comments](https://typedoc.org/documents/Doc_Comments.html) 的源代码注释与 Markdown 生成机制。它们是本项目规则的依据，不表示本项目采用或通过这些规范认证。

### testing：测试方案

| 章节           | 必须包含                                       | 合格条件                            |
| -------------- | ---------------------------------------------- | ----------------------------------- |
| 目标与范围     | 要保护的风险/要求 ID、非覆盖范围               | 测试从要求推导，不从文件数量推导    |
| 测试分层       | 每层证明能力与边界                             | Node/JSDOM 不证明真实几何           |
| 环境与数据     | 版本、依赖、夹具、隔离和时钟                   | 不读取生产机密，不写生产仓库        |
| 用例与断言     | 要求 ID、环境/输入、测试名、独立预期、覆盖状态 | 不是只有测试文件列表                |
| 执行步骤       | 准备、命令、先后顺序、安全清理                 | dist 依赖先构建，未执行阶段不算通过 |
| 通过与退出条件 | 失败、跳过、重试与退出规则                     | 偶发通过和已知缺口不被隐藏          |
| 证据与限制     | 环境、时间、命令、退出码、结果和缺口           | 无基线的性能/覆盖率目标标记未定义   |

人工用例也写任务、允许查阅的入口、应得到的结果和失败条件。证据保存在本次变更记录，不把测试总数永久写入代理规则或 README。

### tutorial：首次学习练习

| 章节       | 必须包含                       | 合格条件                           |
| ---------- | ------------------------------ | ---------------------------------- |
| 学习目标   | 一次练习结束能完成的事、非目标 | 目标具体，不要求先理解整个系统     |
| 准备环境   | 版本、工作目录、依赖和权限     | 默认离线或本地，不启动真实发布     |
| 练习输入   | 提供的夹具、固定参数和初始状态 | 不要求读者自行补隐藏数据           |
| 练习步骤   | 编号动作，逐步展示可观察输出   | 先成功路径，再一个有解释的失败案例 |
| 预期结果   | 输出/文件/页面与关键断言       | 结果能与输入对应，不只说“成功”     |
| 排错与清理 | 常见症状、定位和安全结束方法   | 不清空脏工作区；内存练习退出即可   |
| 后续阅读   | 下一教程、指南、API 或设计     | 详细理论移到设计，不打断主练习     |

### guide：完成明确任务

| 章节           | 必须包含                           | 合格条件                               |
| -------------- | ---------------------------------- | -------------------------------------- |
| 目标与适用条件 | 任务、适用现场、何时不用           | 不把首次学习与生产操作混写             |
| 前置条件       | 权限、环境、版本、备份             | 写入前已确认精确目标                   |
| 输入与配置     | 变量来源、合法示例和机密规则       | 读者知道哪些值要替换                   |
| 操作步骤       | 顺序、分支条件、只读/写入标识      | 命令作用和检查点明确                   |
| 结果核对       | 可观察结果及端到端边界             | 不只判断退出码或首页可达               |
| 失败与恢复     | 失败阶段、停止条件、重试和恢复目标 | 保留既有工作，未知提交结果先核对再重试 |
| 关联资料       | 权威协议、责任模块和验收           | 不复制接口参考或设计全文               |

不得将清空工作树或模块目录作为默认恢复。禁止在可执行 shell 示例中提供批量 Git 删除或覆盖指令。需要恢复时：先记录差异和未跟踪文件，保护修改前状态，确认仅属本次任务的文件，再选择局部恢复；原有改动与本次修改混合时逐块审查。

仅靠 HEAD 不能恢复用户原有未提交内容。

### standard：可执行规则

| 章节       | 必须包含                  | 合格条件                     |
| ---------- | ------------------------- | ---------------------------- |
| 目的与范围 | 约束对象和排除对象        | 可判断某改动是否适用         |
| 规则与要求 | 必须/建议、具体动作和判据 | 不只写原则或口号             |
| 执行流程   | 修改前、中、后的操作      | 明确谁核对什么事实源         |
| 正反例     | 带条件和结果的正负例      | 可据此审查真实改动           |
| 例外与限制 | 例外条件、批准和工具盲区  | 缺口不被当作豁免             |
| 检查与验收 | 命令及人工清单            | 自动与人工责任分开           |
| 关联资料   | 规范关系和一手依据        | 引用说明适用部分，不虚称认证 |

- 辅助类型：index 为“阅读路径→资料清单→维护规则”；
- decision 为“背景→备选方案→决定→后果→再评估条件”；
- record 为“范围→实施记录→验证证据→剩余限制”；
- agent 仅用于 AGENTS.md，按执行顺序组织，不复制共享制度。历史原件不追溯套模板。

### 图示验收

- 图使用 text 围栏中的 ASCII：框线用 +、-、|，方向用 -->，目录使用缩进和分支。禁止 Mermaid。每图写明标题、层次、范围；
- 节点有名称和职责；
- 关系有方向及含义，HTTP/文件箭头必要时写协议或路径。不同关系混用时提供图例。

模块目录不等于进程，源码无依赖不等于运行无交互。成功路径以外的失败、重试和终止必须画出或在紧邻正文说明。修改目录、接口、部署或资源生命周期时核对受影响的图，不只检查围栏格式。

### 目录与归属

```text
README.md / AGENTS.md
packages/README.md           跨包组合架构与工作流
docs/
  architecture/    跨模块设计、质量场景及风险
  standards/       共享工程规则
  reference/       跨模块协议
  testing/         全局验收与覆盖协调
  operations/      跨模块交付协调
  guides/          全局开发任务
    contributing.md 贡献流程唯一入口
  decisions/       跨模块 ADR
  changes/         变更设计和执行证据
  archive/         历史原件
<module>/
  README.md                       readme
  docs/README.md                  index
  docs/explanation/design.md      module
  docs/algorithms/<topic>.md       algorithm，至少一份
  docs/reference/api.md           interface
  docs/reference/<topic>.generated.md  interface，可选生成资料
  docs/tutorials/getting-started.md    tutorial
  docs/guides/change.md            guide
  docs/testing/strategy.md         testing
```

`packages/README.md` 是包目录的受控例外：使用 `architecture` 类型及其固定章节，描述六包的边界、真实交接和跨包任务；不在 `docs/architecture/` 复制该视图。它不是第七个模块 README，也不替代系统级架构总览。包根 README 仍使用统一 `readme` 章节顺序，并链接本总览。

归属按规则所有权和维护责任决定，不按读者数量决定。分页归 Runtime，内容提交归 Publishing，服务器安装与探针归 Operations；构建/浏览器载荷协议在根 reference。新增专题放对应类别，仍使用该类型章节。

禁止模块根或 docs 根的散落专题、旧路径占位和“文档已迁移”跳转页。

- 模块 scope 对应清单 id/root；
- README 的 parent 可为跨模块总览，其他模块文档的 parent 留在本模块。实现及资料位于清单 root；
- applicationEntries 只登记本模块 `cli/` 下的明确脚本，不扩展 owns 到根脚本或其他模块。公开源码入口在 api 并登记 entries，内部实现地址不是跨模块调用接口。
- 开发工具源码放所属模块 `tools/`，操作说明放同模块 `docs/guides/`；不能在工具目录另建一套未受检查的 README 或复制模块资料。
- 模块测试放 `packages/<name>/tests/`，全局测试放 `tests/integration/` 和 `tests/e2e/`。测试策略必须区分这些层次，不把整个混合文件描述为纯单测。
- 测试方案每个重要要求写明环境、初始状态、输入或故障、具体结果判据、命名用例、责任和覆盖限制。不得只列文件名或“测试通过”；通过条件包含非空测试集、零失败、零取消、零跳过、零 TODO、零重试。具体门禁见测试规范。

## 执行流程

1. 确定读者任务、类型、范围、owner 和 parent；列出该类型章节及验收问题。
2. 核对设计约束、接口、源码、清单和测试；记录当前事实、规则和未来能力的区别。
3. 写问题、条件、输入输出、失败和取舍，再补图、示例及质量追踪。不从代码逐行生成设计说明。
4. 实质修改更新 modified；身份和创建日保持。新增/迁移同步导航、关系、生成来源和测试，删除旧文件，不建中转文档。
5. 先运行安全示例和局部检查，再执行文档检查和完整门禁。人工核对图、契约和读者任务。
6. 解决必修问题后将资料设为 active；记录实际验证与未覆盖范围，不机械刷新所有文档日期。

## 正反例

不合格：“模块完全解耦，测试完善，发布可靠。”

合格：“Publishing 不导入 Site 源码，但依赖其内容路径契约。POST /webhook 比对 JSON 请求体的 token。200 表示远程 ref 已更新，不表示部署完成。

同一 server 实例顺序处理已鉴权的发布；跨进程不共享队列。网络结果不确定时先核对远程文章和 ref，不盲目重试。”

不合格：“长文章、空文章都测试一下。”

合格：“Q1 在 Chromium、260/380 CSS px 视口下输入固定长段落；比较分页前后 textContent，并逐页验证实际高度不超过可用高度及测试声明的容差。字体、表格和行内语义的未覆盖部分单列。”

不合格：“失败后撤销整个模块的修改。”

合格：“先保存本次文件清单、差异和未跟踪文件内容；对照修改前状态区分已有改动。只恢复已确认属于本任务的修改；归属不明时停止恢复，不按 HEAD 批量覆盖。”

## 例外与限制

不适用章节必须写具体原因及替代证据，不能删除章节或填写模板口号。新增辅助类型不能用于绕过正常设计/接口结构。例外在变更记录写明范围、理由、风险、替代验证和维护者确认。

历史原文、文章和 vendor 不参与当前结构迁移，但仍不得包含机密。历史记录不是当前操作授权。生成资料只能从来源修正；内容未变化时生成/检查不刷新日期。

检查器验证有限结构，不判断设计正确性、所有路径、完整 Markdown 锚点、图的视觉效果或命令普遍安全性。

危险命令检查只针对声明为 sh/bash/shell 的围栏内命令位置，不是 shell 解析器；已知过时清单名有定向检查，不是任意内联路径解析。人工核对不可省略。

## 检查与验收

```sh
npm run check:docs
npm run verify
```

配置生成来源变化时先运行 npm run docs:generate，审查产物后再检查。格式化只覆盖本次文件，不在脏工作区顺带重写整个仓库。

自动检查：九字段及顺序、类型/状态/日期、H1 和固定 H2、非空章、id 唯一、关系目标和 parent 无环、当前相对链接、模块目录/归属/必备资料、禁止 redirect/Mermaid、机器本地链接、危险恢复命令模式、已知过时清单引用及生成漂移。

人工验收：

- README：从该入口能判断边界、找到 API、执行最小示例和选择测试。
- 设计与图：责任、约束、取舍、失败和目录/运行关系与权威来源一致。
- 算法：可推演步骤；变量、边界、终止、正确性条件及具体案例充分。
- 接口：公开集合、字段、鉴权、错误、副作用与读取时点准确。
- 教程/指南：声明环境可执行，输出符合描述，不损坏已有工作或触发未授权外部写入。
- 测试：重要要求能追踪到命名案例和独立判据；人工/未覆盖状态明确。
- 迁移与元数据：唯一权威内容、无跳转页，id/created 保持，modified 符合实质变更。

结构检查通过后仍可能存在错误契约；每次交付必须包含事实核对及读者任务走查。
