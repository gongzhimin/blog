## 目的与范围

审查系统架构、模块重构、接口及文档是否满足需求、边界和验收条件。
审查的核心原则是：“**先判定是否在解决正确的问题，再核实技术实现与验证证据的真实性**”。
本规范的适用对象包括：

1. 涉及跨模块契约、公共 API、数据持久化模型与部署配置的架构设计；
2. 模块级技术实现方案与重构改动；
3. 受控工程文档系统（包含架构、模块、算法、接口参考与操作指南）的内容完整性与事实一致性审查。

格式和链接检查仅覆盖有限结构及相对引用，不证明所有链接、技术内容或设计正确性。

## 规则与要求

### 1. 核心审查十大维度

任何提交评审的设计文档或方案，必须能够正面且明确地回答以下十个维度的工程问题，严禁使用含糊口号敷衍：

| 审查维度       | 评审必须能够回答的核心问题                                              | 典型不合格信号（直接打回）                             |
| -------------- | ----------------------------------------------------------------------- | ------------------------------------------------------ |
| 问题与范围     | 目标使用者在什么具体场景下遇到了什么限制？明确的非目标是什么？          | 使用“优化架构”、“重构代码”等泛泛空话替代真实痛点       |
| 质量属性驱动   | 系统优先保障哪些质量属性（如连续性、安全性、只读性）？有何可验证响应？  | 仅堆砌“高性能、高可用、高扩展”等抽象口号               |
| 领域模型契约   | 实体的全局唯一标识是什么？时间与排版度量单位是什么？不变量在哪里保障？  | 滥用泛型 `data`、混用正文显示页码与物理页码            |
| 职责边界清晰度 | 为什么该职责划入本模块？上游生产者与下游消费者各自承担什么？            | 仅仅因为“代码写在某个文件夹下”就作为模块划分理由       |
| 交互与失败传播 | 函数与进程执行的前后置条件是什么？调用发生错误时如何向下游传递？        | 流程图中只有一马平川的成功箭头，完全缺失错误与回退分支 |
| 资源与生命周期 | 核心资源（DOM、网络连接、定时器、缓存）由谁创建、谁销毁？依赖什么环境？ | 全局共享可变状态、缺乏取消机制、无界无限重试           |
| 设计权衡与代价 | 考虑过哪些备选方案？为什么舍弃它们？当前方案付出了什么代价？            | 通篇只自夸所选方案的优点，完全不谈技术负债与妥协代价   |
| 兼容与平滑迁移 | 哪些既有消费者受到影响？旧入口如何安全废弃与迁移？                      | 仅在本地修改新路径，未同步部署清单或未清理旧入口       |
| 证据有效性判定 | 自动化测试究竟能证明什么？明确不能证明什么？                            | 将单元测试字符串比对通过等同于真实浏览器排版正确       |
| 架构演进触发点 | 遇到什么样的规模压力或业务形态变化时，需要推翻现有设计？                | 将远期未落地的愿景包装为当前已实现的能力               |

## 执行流程

设计审查与文档验收采取分阶段、多视角的审查闭环：

### 阶段一：规格审查（Specification Review）

1. 审查者对照用户初始需求与任务描述，逐条核对设计方案中的问题定义、使用场景与验收指标；
2. 重点审查“非目标”边界，严禁在未经授权的情况下过度设计或擅自引入与核心目标无关的重构；
3. 发现遗漏的核心需求，标记为“必须修复（Must Fix）”，阻断方案推进。

### 阶段二：事实审查（Fact Verification）

1. 抽查设计文档中声明的每一个公共 API 签名、配置字段与操作步骤，直接核对仓库内的真实源码与配置文件；
2. 验证操作指南中的终端命令是否可直接复制运行，排查由于路径过时或环境变量缺失导致的指令失效；
3. 文档与源码冲突时，先对照需求和已确认契约确定错误一方。源码违反安全边界、核心不变量或合法调用契约时，补失败回归并在授权内修复源码；不能通过降低文档要求掩盖缺陷。文档虚构未实现能力或错误描述实际协议时，修正文档；新增能力或范围不明时明确方案并确认授权。

### 阶段三：读者任务走查（Walkthrough）

1. 审查者完全脱离作者的口头解释，仅凭当前受控文档尝试执行一项具体的开发或排错任务（如“新增一本 JSON 书籍”或“排查 Webhook 监听失败”）；
2. 若在走查过程中必须依赖猜测、外部未记录的“潜规则”或翻阅历史 Git 提交记录才能继续，即证明文档不合格，记录为文档缺陷。

## 正反例

### 合格设计论证示例

在重构 Publishing 模块时，设计文档明确阐述：

- **职责切分**：`input.cjs` 拥有多格式输入解析与硬换行清洗；`planning.cjs` 拥有同名文稿识别、日期继承与删除计划编排；`github.cjs` 封装远程 Git 数据对象调用与非强制提交；`http.cjs` 管理请求鉴权与状态码映射；
- **各层证据**：输入解析由纯函数单测验证；文件计划由包含同名覆盖的历史快照测试验证；网络提交流程由注入的 request 替身验证 `force: false` 参数；
- **代价说明**：采用远程 Git 数据 API 避免了本地工作树脏状态，但增加了多轮网络往返时延。

### 不合格典型反例

- **反例一：以文件切分替代设计**：“将某巨大文件拆分成三个小文件以减少代码行数”——未解释每个新文件的职责边界、数据流动与错误隔离，仅仅是物理搬家；
- **反例二：证据越界夸大**：“自动化单测已通过，证明页面排版完美无溢出”——忽略了 JSDOM 不具备真实字体折行与 CSS 盒模型渲染能力的事实，属于虚假保证；
- **反例三：未闭合的迁移**：在代码中新增了公开函数，但未同步更新模块 README，未更新调用方代码，导致新旧两套入口在代码库中共存。

## 例外与限制

1. **评审意见分级机制**：
   - **必须修复（Must Fix）**：事实错误、破坏安全边界、缺失核心容错逻辑、不可执行的操作步骤，必须在合并前彻底解决；
   - **建议改进（Should Improve）**：表达润色、图表排版美化、非关键边界用例补充，允许作者在权衡后记录为后续任务；
   - **参考信息（Info）**：记录未来演进的构想与讨论，不作为本轮验收卡点。
2. **工具链局限声明**：
   - `npm run check:docs` 检查元数据、章节、归属、关系、部分路径和危险命令模式及生成漂移；不理解设计语义，不证明所有命令安全。技术事实、图示和读者任务仍需人工核对。

## 检查与验收

在通过设计审查与文档验收前，审查者需对照下表完成最终核准：

| 读者任务场景             | 仅凭受控文档应能明确得出的结论                      | 对应源码/配置核查锚点                                                                 |
| ------------------------ | --------------------------------------------------- | ------------------------------------------------------------------------------------- |
| 新增一本外部 JSON 书籍   | 明确数据结构、字段约束、装配 API 与预估页码语义     | `packages/book-build/src/api/index.mjs`, `book-config.schema.json`                    |
| 调整书籍翻页视口与断点   | 明确桌面/移动两套测量配置、显示与测量 CSS 等价规则  | `packages/book-runtime/src/internal/`, `packages/site/src/components/BookShell.astro` |
| 诊断发布成功但网页未更新 | 清晰区分内容发布成功（Ref 更新）与站点编译部署失败  | `packages/publishing/src/internal/github.cjs`, GitHub Actions                         |
| 扩展跨模块公开依赖       | 明确需要在清单中登记的白名单字段与公开 entries 限制 | `packages/tooling/src/modules.json`, `packages/tooling/src/`                          |

验收结论判定：当且仅当所有读者任务走查均能无障碍闭环，且全量自动化门禁 `npm run verify` 绿灯通过时，方可正式签署“验收通过”。
