## 目的与范围

约束功能、重构、配置、契约和部署变更的范围、设计、验证及交付记录。
本制度的约束对象包括：

1. 静态文稿资产、排版配置及展示样式的修改；
2. 模块内部局部实现逻辑与公开 API 接口契约的变更；
3. 跨模块数据协议、存储结构与路由路径的演进；
4. 部署工作流定义、Systemd 守护进程与服务器运行配置的调整。

没有交付物的一次性只读诊断可不写大型设计，但仍遵守安全和授权。已有未提交改动属于用户，必须保留。变更分级只决定记录和验证深度，不扩大授权范围。

## 规则与要求

### 1. 变更分级标准

所有工程改动必须按照影响广度与系统风险划分为明确的层级，严禁以代码改动的行数（Diff 大小）替代风险定级：

| 变更层级           | 典型场景                                            | 最低设计与记录要求                                                 | 核心验证证据                                             |
| ------------------ | --------------------------------------------------- | ------------------------------------------------------------------ | -------------------------------------------------------- |
| 样式与内容变更     | 文章 Frontmatter 调整、样式细节微调、静态文案修正   | 明确修改事实、涉及页面与受影响链接                                 | 静态格式化、本地渲染核对、人工走查                       |
| 局部功能与缺陷修复 | 算法边界修正、局部异常捕获、内部辅助函数重构        | 明确缺陷复现步骤、根本原因、修复逻辑与兼容策略                     | 构造由失败到通过的最小测试用例，运行模块单元测试         |
| 模块边界与契约演进 | 新增跨模块公开 API、修改 Schema、拆分或合并模块目录 | 必须编写变更设计（Design）与实施计划（Plan），列明消费者与迁移方案 | 契约测试、模块边界检查（check:boundaries）、全站静态构建 |
| 运行时与部署架构   | 调整 Systemd 服务、网络端口、Nginx 代理、鉴权机制   | 详细说明运行状态、故障降级、回退方案与目标环境依赖                 | 隔离网络替身测试、受控服务器联调、端到端集成验收         |

### 2. 需求先行与非目标界定

在动手编写业务代码前，必须先界定清晰的需求边界：明确输入数据格式、执行前后置条件、可观察的成功结果，并显式列出“非目标”（Out of Scope）。严禁在未搞清楚状态流转与失败降级路径的情况下，盲目添加未受控的界面元素或配置开关。

### 3. 全链路影响面分析

在涉及数据结构或公共接口变更时，必须从以下维度进行穿透式审查：

- **上游与下游**：列出所有直接调用方与间接消费方，严禁直接删除字段或静默改变返回值的语义；
- **配置与 Schema 同步**：修改配置字段必须以权威 Schema 为单一事实源，并立即触发文档自动生成，严禁手动维护两套解释；
- **部署契约一致性**：若涉及脚本路径或服务名变更，必须同时更新 GitHub Actions 工作流、服务模板与运维恢复手册。

## 执行流程

实施一项工程变更必须严格按照“准备阶段 → 实施阶段 → 验证交付”三个阶段闭环执行：

### 阶段一：修改前（准备与反例确立）

1. 明确读者任务、受影响模块所有权与上位文档归属；
2. 阅读权威源码实现与相关现有测试，确立修改基线；
3. 针对待修复的缺陷或待实现的新特性，构造最小失败测试反例，验证旧逻辑确实会失败。

### 阶段二：修改中（编码与契约同步）

1. 实施代码改动，优先保证公开接口与数据不变量向后兼容；
2. 废弃接口时列出消费者并在仓库内同步迁移，删除旧代码和空壳；不同部署版本的兼容需要单独设计，不能把仓库同步修改称为生产原子切换；
3. 同步更新模块内的公开 API 说明、架构设计文档与受影响的配置文件。

### 阶段三：修改后（全量门禁与交付核验）

1. 运行模块本地单测，确认构造的失败反例成功转绿；
2. 运行 `npm run check:docs` 检查文档规范与死链；运行 `npm run check:boundaries` 确认未破坏模块边界；
3. 执行 `npm run verify` 完成全流程自动化门禁验证；涉及排版与浏览器交互时，运行 `npm run test:e2e`；
4. 审查 `git diff`，确认所有变更均在授权范围内，无意外的文件污染。

## 正反例

### 合格重构示例

将 Webhook 接收脚本从散落状态规范化至模块内：

1. **旧入口与新入口**：将散落实现拆到 `packages/publishing/src/api/` 和私有实现；启动入口直接位于 `packages/publishing/src/cli/publish.cjs`，不在根保留包装或别名；
2. **完整消费方同步**：同步更新 `blog-webhook.service` 启动脚本、GitHub Actions 部署上传清单、单元测试用例及模块 README；
3. **彻底清理无残留**：删除旧的废弃文件，绝不建立长期的别名重定向空壳，文档与测试全部指向新架构。

### 不合格典型反例

1. **只搬文件未改部署**：在重构时修改了服务的启动脚本位置，测试中通过了函数级单测，但未同步更新服务配置模板与 CI 部署脚本，导致线上服务重启时因文件找不到而崩溃；
2. **虚假修改与测试脱节**：直接手改生成的参考 Markdown 文件以应付文档检查，未从根本上更新 JSON Schema，后续生成器执行时产生冲突漂移；
3. **通过降低标准换取绿灯**：遇到测试断言失败时，不深究业务逻辑错误，而是直接注释测试用例或放宽数值校验区间。

## 例外与限制

1. **紧急生产故障修复（Hotfix）**：在遭遇线上严重不可用时，允许在获得明确授权后简化设计文档的篇幅，但绝对严禁跳过自动化门禁测试，严禁在生产日志中输出明文凭据，且必须在故障恢复后 24 小时内补齐完整的变更记录与回归测试；
2. **工具链边界**：计算型 require/import 和项目别名在当前源码门禁中被拒绝；运行期 HTTP/文件协议、完整打包解析和设计语义不由门禁证明，需要契约测试及人工核对。

## 检查与验收

任何变更在最终交付前，必须按照以下清单逐项勾选验收：

- [ ] 验收标准均已满足，所有声明的非目标均未被意外越界实现；
- [ ] 所有受影响接口的 JSDoc 注释、类型声明、Schema 约束与调用方已完成同步；
- [ ] 废弃的旧路径、历史死链与临时文件已被彻底清理，无迁移空壳残留；
- [ ] 执行全套自动化门禁命令，确认全部退出码为 0：
  ```sh
  npm run check:docs
  npm run check:boundaries
  npm run verify
  ```
- [ ] 若涉及页面布局、样式断点或交互，已执行浏览器端回归测试：
  ```sh
  npm run test:e2e
  ```
- [ ] 交付报告中已清晰区分“本地实现就绪”与“生产线上生效”，未将本地成功混淆为已上线。
