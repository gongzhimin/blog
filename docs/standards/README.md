## 资料清单

### 规范与设计的关系

[系统架构](../architecture/overview.md) 回答为什么这样组织，规范回答后续怎样修改才能维持约束。接口说明当前契约，测试提供证据，ADR 记录选择。

规范不是对当前代码全部合规的证明，已知缺口见 [风险台账](../architecture/evolution.md)。

适用范围是自研 src、scripts、src/book-runtime、测试和当前文档。第三方 vendor 不改写；历史记录不按现行格式追溯修改。

### 规则强度

- MUST / 必须：本项目最低要求。未满足时不能宣称正常验收。
- SHOULD / 应当：默认选择。偏离需解释场景、风险和替代证据。
- MAY / 可以：可选实践，按实际收益采用。

这是本项目约定，不能声称因此符合某项国际标准。自动化能力与规则强度分开：有些 MUST 需要人工审查，现有检查可能覆盖不到。

[设计审查指南](design-review.md) 将上述制度转换为审查问题、正反例和读者任务走查，先看目标与模型，再看实现与证据。

### 例外与维护

规则不适用时，贡献者必须记录具体规则、原因、风险、替代控制、适用期限或移除条件，并由维护者审查。私钥泄露、越权写入、删除用户改动及伪造验证不属于可接受例外。

规则变更需要说明原规则为何不足、影响范围和迁移方式。不能为了让当前一次提交通过，先把规范改宽松。审查制度也应裁剪：小文案不要求架构 ADR，边界和权限变化不能按文案处理。

## 维护规则

新资料按 [文档规范](documentation.md)登记类型、关系和责任；迁移更新全部当前引用并删除旧文件，不保留重定向占位。生成资料更新来源，历史原件不覆盖。
